## 評定

**懸念あり (GO-with-concerns)**

コアアーキテクチャは健全であり、エビデンスに基づいている： 測定されたコンテキストプレッシャーを静的なモデル分類ではなくトリガーとして使用することは、EV-006に加えてQwenのアーティファクトレポート（アロードランタイム上で検索動作をするモデル）によって直接支持されており、コア判定ループ＋最小限のランタイムタップという分解はD1=Bのクリーンな実行であり、推奨のみのv1は誤発火のコストを制御されたものにしている。しかし、このドラフトは、L1-9がゲートを管理することを意図していたまさにそのレベル（述語セマンティクス、ウォッチドッグアクションセマンティクス、EV-007事前登録の完全性）において、仕様の完全性にギャップを持っている。3つのブロッカーはすべてドキュメントレベルでの修正であり、設計の見直しを強制するものではないため、実装はこれらが設計ドキュメントに反映された後に開始され得る。

## ブロッキングファインディング

1. **MAJOR — §3 (トリガー述語) + §2 (タップコントラクト)： ファイア述語はその接続点において過少に仕様化されている。**
   なぜこれがブロッカーなのか： (a) 3つの軸がどのように結合されるか（ORかANDか）、また、送信前ペイロード推定がNサンプル移動平均の最新サンプルとして採用されるのか、それとも単独の即時チェックなのかが述べられていない。§3の「送信直前」チェックポイントノートは意図（「事後方式より1ターン早い」）を示唆しているが、2人の実装者が2つの異なるセンティネルを構築してしまうだろう。また、§6の事前登録は正確な述語なしには登録できない。(b) インジェクションは `input + cache_read` として定義されているが、Anthropicの使用セマンティクスでは、1ターンあたりの合計入力は `input + cache_read + cache_creation` である。この省略は体系的な過少評価をもたらす。ターン1では最悪のケースとなる（システム＋ツールのプレフィックスがほぼすべて `cache_creation` であり、`cache_read ≈ 0` のため、測定された「インジェクション」はほぼゼロと読み取られる）。これは、早期発火が最重要であるまさにその初期ターンにおいて、N=3の平均とターン2のスロープを汚染する。ターンごとの新しいツール結果は継続的に `cache_creation` となるため、誤差は定常状態でも消えない。(c) 送信前推定は完全なペイロードをカウントするのに対し、使用量ベースのサンプルは `input + cache_read` をカウントするため、閾値近くの動作が推定器に依存してしまう同じ数量に対する2つのバイアスの異なる推定器が存在することになる。
   修正方向： ドキュメント内の数式を1つに固定する。`injection_t = input + cache_read + cache_creation`（アダプターはこれを正規化する。`cache_creation` を報告しないランタイムは0を報告し、コントラクトでフラグ立てされる）。送信前サンプル＝推定完全ペイロード。明示的な述語を1文で記述する（例： 平均または射影が発火条件を満たすかどうか）。どの推定器が各サンプルを生成したかをログに記録し、§4のwの導出が同じ定義に基づいていることを確認する（PILOT.mdの~112k/turn = 56%という数値が、どの合計に対して測定されたのかを検証する）。

2. **MAJOR — §6 (EV-007)： 記載されているままでは事前登録不可能であり、D5のデフォルトオンゲートは到達不可能なエンドポイントに依存することになる。**
   なぜこれがブロッカーなのか： このIssueの完了条件は、事前登録されたEV-007を設計フェーズの成果物としている。現状のままでは、以下が欠落している： (a) 誤発火と見逃しの運用上の定義。`outcome_followup: overflowed` は、ランタイムエラー、自動コンパクトイベント、または品質低下のいずれを意味するのか？ 誤発火は 反実仮想を持たない。なぜなら、発火したターンがその後の軌道を変えるためである（これが、判定可能な代理指標、例えば「発火時のインジェクションがその後コンパクト/オーバーフロー閾値を超えなかった」を必要とする理由である）。(b) キャリブレーションアームのためのw選択基準（どのメトリックが{40,50,60}から勝者を選ぶのか）。(c) 分解者アームA/B/Cと3つのメインアームとwスイープのクロス構造。3×3×3の可能なセルがあり、ファクトリアル構造やセルごとのシーケンスカウントが記載されていない。(d) セルあたり約20タスク（20項目の2項分布の信頼区間は約±20pt）における精度のための非劣性マージン。マージンがなければ、非劣性の判定ができない。(e) エンドポイントのアカウンティング： 「トークン総量」はコストで重み付けすべきである。パイロットの4〜6倍はトークン倍率であり、claude-CLIのベアターンは課金において割引される `cache_read` が支配的である。生のトークン合計は、コストの倍率を過大評価し、その結果デフォルトオンの経済性を歪めてしまう。(f) 自動エンキューの実験例外のための再帰ガード（ハーネスサブタスク内で誤発火してもループしないように、タスクごとに最大1回の分解または深さ1）。
   修正方向： 運用上の定義、w選択ルール、セルカウントを含むファクトリアルテーブル、非劣性マージン、コスト加重の併存主要エンドポイント、および再帰ガードを事前登録ドキュメントに書き込む。

3. **MAJOR — §3-3 + §5 (TTFBウォッチドッグ)： 「fail-loud」はD3（v1 = 推奨のみ + ログ）と矛盾しており、輸入されたフロアはこのスタックに対して較正されていない。**
   なぜこれがブロッカーなのか： fail-loudが90〜240秒でのキルを意味する場合、v1は推奨のみの決定を超えた動作を導入する。フロアテーブルは、Hermesの直接APIプロバイダーレイヤーからのものであり、CLIランタイムからではなく、CLIのコールドスタート＋大規模なプリフィルは正当に90〜240秒を超える可能性がある。具体的には： 100k以上のプロンプトのプリフィルは、2〜5k tok/sで120〜300秒を要する可能性があり、テーブルには>100kのラングがなく、600kのプロンプトでそれが機能するかは§8自身の1Mウィンドウの質問である。Hermes自身も、GLM-5.3のフロアが修正されるまで誤ってキルしており（hermes#89241）、輸入されたテーブルのGLMエントリはまだ解決されていない「提案=300s」である。解決されていないキル動作を伴う仕様は、実装がどう解釈すべきかを推測する必要があるため、まさにこのレビューが防ごうとしているギャップである。
   修正方向： v1ウォッチドッグ＝検出＋アラートログエントリ＋ナッジのみ。キルは既存のステップタイムアウトのままにしておく（これにより、パターン4のオブザーバビリティ獲得——600〜1200秒の代わりに90秒での検出——は維持される）。キルセマンティクスは、次の条件が満たされた場合にのみ、独自のフラグの背後にあるv2に繰り越される： フロアテーブルが完了する（GLMを含む）、>100kラングまたは継続的なトークンごとのスケーリングが追加される、CLIオーバーヘッドマージンがシールドリグ上で較正される。

## 非ブロッキングファインディング

- **§2 タップコントラクト — ctx_windowの所有権**: `ctx_window` はタップイベントとコアの4段階のラダーの両方に現れる。優先順位を述べる（例： ラダーがアダプターの報告する信念を上書きし、どのラングが勝ったかをログに記録する）。qwen/200kの誤った想定の歴史を考えると、発火ログにおけるctx_windowの出所は安価で価値が高い。また、相関識別子（タスク/実行IDをイベントに載せるか、タップがタスクごとのチャネル経由で送信されることを明示的に示す）、コントラクトのバージョンフィールド、および「未知のフィールドは無視されなければならない」を追加する。
- **§2 送信前推定の実現性**: 3項の成長則（前回のインジェクション＋出力＋ツール結果）は、アダプターがツール結果のサイズを送信前に観察できる場合にのみ「手元にある」ことになる。フックベースのタップ（IssueのFiles-to-touchリストから）でこれは実行可能だが、セッションモードのランタイムではツール結果がCLI内部に存在する。フォールバック推定とその誤差限界を述べ、キャリブレーションが同じ推定器を使用するようにする。
- **§4 ラダー — HF config.jsonはサーブされるウィンドウではなく、トレーニングの上限である**: `max_position_embeddings` はプロバイダーがそれ以下でサーブする可能性がある（また、YaRN/RoPE-scaleの設定は抽出を混乱させる）。ウィンドウの過大評価は安全でない方向（遅発火）である。設定により下位互換性を持たせ、model→HF-repoのマッピング自体がメタデータのカタログ（非目標にある「静的分類のメンテナンス」の限りり小さいもの）であることに言及する。
- **1Mウィンドウモデル（§8でフラグ付けされたもの）**: 1Mのw=50%は、合理なタスクの長さでは到達できないかもしれない ~500k/ターンを意味する。センティネルは事実上[1m]モデルでは沈黙することになる。タスク終了前のコストベースの発火が望まれる場合は、絶対的なトークンフロア（例えば、`avg_injection > X` が比率と独立して発火する）が安価な補完となる。このファインディング3で述べたTTFBフロアの 注意点は、ここでも当てはまる。
- **§5 発火ログの追加フィールド**: 最後のNサンプルあたりのインジェクション値、使用されたクラス事前分布、推定方法、および使用されたctx_windowのラング。また、書き込み時ではなくタスク終了時に `outcome_followup` が追加されるプロセスクラッシュのギャップを受け入れるが、ログのローテーション/保持ポリシーを述べ、タスクレッジャーがファイアIDを逆参照してタスクID+タイムスタンプの結合に依存しないようにする。
- **§5 ナッジの受け手**: トランスクリプト内の1行はタスク内モデルに到達するが、分解できる主体はオーケストレーターである。ファイルに加えてオーケストレーターから見えるイベント（フック/終了サマリー）を検討する。さもなければ、実運用では誰もそれを読まず、v1のナッジ効率（受け入れ率）は測定されないままになる。なお、EV-007のセンティネルアームは自動エンキュー（v2動作）をテストするため、v1の実際の効果は測定されていないことになる。これで問題ないが、明示的にそう述べてほしい。
- **D-5 バンドリング条件**: 共有タップを考えると容認できるが、2つの軸が独立して切り替え可能であることを要求し、ウォッチドッグは検索クラスの「保守的な閾値」の事前分布を継承してはならない（CLAUDE_BINハングはシムバックエンドで発生したため、検索タイプのランタイムはウォッチドッグを最も必要とする）。クラス事前分布は軸1〜2にのみ適用される。
- **D-2 スイープ範囲**: wのみがスイープされる（{40,50,60}）。誤発火/見逃しレートは、NとMにも少なくとも同程度に依存する。N∈{2,3,5}をスイープに追加するか、§4で1行で固定する理由を説明する。また、w=50%が閾値ではなく、観測されたレジームレベル（n=1パイロット、単一モデルバンド）であるという注意書きを§4に追加する。ドキュメントはすでに値を暫定的なものとして扱っているが、導出はその限界を明示的に示すべきである。
- **EV-007モデルセットの一貫性**: Qwenアーティファクトレポートは、EV-007のqwenウィンドウのenv修正（`CLAUDE_CODE_MAX_CONTEXT_TOKENS=262144`）を指示しているが、§6はsonnet/haiku/codexのみをリストアップしている。アロードランタイム上の検索動作モデルとしてのqwenを追加することは、D2=Aに対する最も強い支持となる。含めるか、その除外を明示的に述べてください。
- **ツール結果のスパイク / 非単調な成長**: 追加専用のランタイム（claude）では、スパイクは一時的ではなく永続的な成長であるため、N=3のMAによるファイアは正当である。トリミングランタイム（codex）では、スパイクは元に戻る。推奨のみのv1では、紛れ込んだナッジは安価である。これらのレジームをキャリブレーションの説明の1行として文書化するだけでよい。
- **Degrade UX**: タップの欠如は現在、不可解なオフになっている。1回の「センティネル非アクティブ（usageタップなし）」ログ行を出力し、非アクティブ化を監視可能にする。
