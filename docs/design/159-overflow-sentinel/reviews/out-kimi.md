  ## Blocking findings

  1. **MAJOR — §3 (トリガー指標): the trigger metric, the Issue's central Done-when deliverable, is underdetermined.** §3's preamble establishes that the check runs *pre-send* against the estimated next-payload token count ("送信予定ペイロードの推定トークン数を直接測るのが最速・最正確"). Axis 1 (水位), however, is defined as the *moving average of the last N measured per-turn injections* vs `ctx_window × w%`. These are different quantities with different behaviors: the MA smooths tool-result spikes and lags by up to N−1 turns; the pre-send estimate catches exactly the spike the preamble says motivates pre-send checking. The draft never states which value is compared against the threshold, whether the estimate enters the MA window as its newest sample, or what N=3 means on turns 1–2. Two implementers reading this draft will build different sentinels. **Fix direction:** one normative sentence pinning the comparison — e.g. "level check: `E[next_payload_tokens]` (measured pre-send) vs `ctx_window × w`; the N-turn MA of *measured* injections is used only for slope (axis 2)" — plus the turn-1/2 degenerate-case rule and the estimation method (tokenizer? chars/4 heuristic?) with an error bound, since near-threshold decisions live or die on estimate accuracy.

  2. **MAJOR — §6 (EV-007): as specced, no arm can ever overflow, so the slope axis, the `overflowed` outcome class, miss-rate, and the Issue-required "per-model overflow-frontier calibration" are all unmeasurable.** The sealed EV-006 corpora (M/L band) completed bare at 20/20 with ~112k/turn average on a 200k window — ~56% utilization, zero overflows. Re-running those corpora on the same models with a ~50% threshold yields fires near the end of the band at best, and the w-sweep {40,50,60}% calibrates *a threshold*, not *the overflow frontier* the Issue names. §5's log schema promises miss-rate measurement (`outcome_followup: overflowed`), but nothing in §6 generates an `overflowed` outcome to measure against. **Fix direction:** add a forced-overflow sub-arm — the §4 ladder's config-override rung makes this cheap (artificially lower `ctx_window`, e.g. 64k, on L-band tasks so bare genuinely overflows) — or add an XL task band; then state the miss-rate protocol (sentinel must fire ≥K turns before actual overflow) and how the w-sweep interacts with the induced frontier.

  3. **MAJOR — §4/D-7: the level threshold is purely relative to `ctx_window`, which silently contradicts the Issue's own motivating evidence on 1M-window models.** EV-006's finding is that harness benefit tracks *absolute* re-injected volume (all-load runtimes re-send the whole conversation; cost ∝ tokens), not window pressure. A 1M-window all-load model at 112k/turn — the exact regime where EV-006 proved 4–6x waste — sits at 11% of window and never trips a 50% threshold. The sentinel would be silent in precisely the cost regime it exists to catch, on precisely the "new models appear forever" class the Issue cites as the reason not to use static classification. §8 lists this as an open question but proposes nothing, and the §6 w-sweep (all relative, all on ~200k models) cannot firm it either. **Fix direction:** add an absolute-token component to axis 1 (e.g. fire when `min(ratio ≥ w, absolute ≥ X tokens/turn)`, with X derived from the EV-006 savings region ~60–80k and firmed by EV-007), or explicitly scope v1 to windows ≤ some size and say so in §7 non-goals. One paragraph plus one sweep dimension.

  ## Non-blocking findings

  - **D-1 / tap field semantics:** `cache_read_tokens` is claude-wire vocabulary. Codex `turn.completed` and agy `result` usage objects have different cache accounting (and codex's is prompt-cache dependent). The tap contract (§2) should mark `cache_read_tokens` optional with a documented fallback (treat as 0 vs treat as input) — otherwise the same runtime behavior yields different level readings per adapter.
  - **D-1 / non-monotonic injection:** claude CLI auto-compaction will appear as a sudden injection *drop*. The draft doesn't say whether a compaction event resets the MA/slope, is logged, or is treated as the runtime self-mitigating (in which case a pending nudge should probably be suppressed). Worth one design sentence; it's also a false-fire source in the post-hoc analysis.
  - **D-1 / slope linearity:** growth from tool results is spiky/superlinear, not linear. M=10 linear projection is acceptable for recommend-only v1 (false-fire cost is one log line + one nudge), but the projection assumption should be stated as a known-weak approximation so EV-007's false-fire stats are interpreted correctly.
  - **D-4 / log schema gaps:** the schema records `avg_injection` but not (a) the pre-send estimate that actually triggered the fire, (b) *which axis* fired (`decision: nudge|alert` conflates axes 1+2 vs 3 but doesn't separate level-fire from slope-fire — needed to evaluate the two axes independently), or (c) nudge uptake (shown? acted on?), without which `decomposed` outcomes in v1 can't be attributed. Also, the `outcome_followup` writer is unspecified — who appends, at what hook, with what correlation key. Finally, note a definitional trap: `completed` after a fire is not a false fire if the sentinel's purpose is cost (the task may have completed 4x more expensively than decomposed) — the post-hoc false-fire analysis needs token totals joined from the ledger, which the separate-file design (§8) must not preclude.
  - **D-5 / step-health bundling:** justified for v1 — the tap plumbing and `byte` event are shared, the rootcause report explicitly hands the TTFB watchdog to #159, and `decision: alert` keeps its stats separable. But the boundary with harness#162 (zero-output failure-class separation, early DLQ) must be drawn in the doc: #162 owns post-hoc attempt classification, sentinel axis 3 owns live detection+alert — otherwise two systems will both "own" zero-byte hangs. Also note axis 3's action path (fail-loud alert) has nothing to do with decomposition; if it grows its own logic (kill/reconnect per Hermes), split it.
  - **D-6 / missing pre-registration fields:** beyond the blocking overflow-induction gap, §6 lacks: sample size / repetition count per arm, the accuracy non-inferiority margin, primary-endpoint priority (tokens vs accuracy when they conflict), and task-order/randomization controls. The decomposer arms B/C (owner-requested, fine) also need a stated decision rule — the draft says "C>B ⇒ nudge target should be the orchestrator," which is good; pre-register that threshold-free comparison explicitly so it isn't post-hoc.
  - **D-2 / w anchor weakness:** the 50% default is anchored on a *run-average* (56%) that includes early low-injection turns — the run crossed the "waste region" well below 56% instantaneous. As defaults-with-override this is defensible since EV-007 sweeps it, but the doc should stop presenting 56% as the derivation of 50% and present it as "same neighborhood, sweep will firm."
  - **D-3 / class prior keying:** REPORT-qwen38 shows runtime class ≠ behavior class (Qwen on claude CLI behaves search-type due to training). §4's prior is listed as all-load/search/unknown but never says what it's keyed on (runtime? model? model×runtime?) or what it changes (initial w? MA seed?). D2 makes live measurement the decision, so the blast radius is small — but "search ⇒ effectively off" as a *prior* reintroduces static classification through the back door if keyed on runtime. Clarify, or drop the prior to unknown-only for v1.
  - **Hermes floor table completeness:** §4 imports the reasoning-floor table; confirm the GLM-5.3 entry (hermes#89241's proposed 300s) is actually in the imported table, since glm-via-shim is an in-scope runtime and the cited incident is exactly its false-kill precedent.
